# Save every stamp, replay the morning

The game should save the seed plus a compact list of the player's stamps to one `localStorage` key after every decision, and write the shift clock again the moment the tab hides. A refresh then resumes exactly where the clerk was, with the clock stopped behind a "Continue" card. Replaying is kept as a deliberate act: "Redo today" in the pause menu rewinds to this morning's Gazette, and "Start the week over" sits behind a real confirmation. This is a hybrid of two precedents. Papers, Please and its desk-game successors checkpoint at the start of each day and treat replaying a day as a feature. Browser games (Wordle, 2048, A Dark Room) save after every move, so a refresh can never act as undo. The browser matters here because refresh is also how players recover from glitches. With a deterministic seed, a day-start checkpoint would turn every refresh into a free rehearsal of a known queue. The technical risk is not storage loss, which is rare outside Safari's 7-day purge. It is a save replayed on a newer build silently producing a different week. A build constant plus a fingerprint check, with an in-fiction "discard and start fresh" message, handles that without migration code. Four changes need the owner's sign-off before anyone builds them. Escape currently toggles Inspect. "Redo today" is new gameplay. One existing e2e test assumes a refresh restarts the day. And "start over" needs a decision on same seed or new seed.

## Desk games checkpoint the morning, browser games save every move

Papers, Please is the direct model, and on desktop it saves only at day boundaries. Lucas Pope: "The game should automatically save at the start of each day," and players confirm that a failed day produces no save ([Steam](https://steamcommunity.com/app/239030/discussions/0/846963165520653258/)). From the day-select screen any saved day can be replayed, and doing so grows a new branch rather than overwriting the old one. Pope's 2013 note on it: "supports branching from any day. Might be overkill." ([X/@dukope](https://x.com/dukope/status/350919332613726208)). Players disagreed with "overkill". TouchArcade called the system "shockingly great", and noted that some story beats make you "reload your game save over and over" to try to prevent them ([TouchArcade](https://toucharcade.com/2014/12/15/papers-please-for-ipad-review/)). The price was interface debt. There is a cap of about **five branches**, with a "Save Branch Full" message ([GOG forum](https://www.gog.com/forum/papers_please/save_game_branches_full)). The only way to start over is a trashcan icon or picking Day 1 ([Steam](https://steamcommunity.com/app/239030/discussions/0/485624040229142358/)). And a header file holds the tree: when one corrupted, the fan's saves became "a bunch of floating day saves" that Pope repaired by hand ([KitGuru](https://www.kitguru.net/gaming/jon-martindale/papers-please-dev-personally-fixes-fans-save-files/)). The 2014 iPad port listed **"mid-day resume"** as a new feature ([App Store](https://apps.apple.com/us/app/papers-please/id935216956)). How that port treats the in-game clock is undocumented.

The comparable games split cleanly by save unit. Day-structured desk games checkpoint the day. Per-action narrative games and every browser game found resume exactly.

| Game | When it saves | Quit mid-unit | Starting over |
|---|---|---|---|
| Papers, Please (PC) | Start of each day ([Steam](https://steamcommunity.com/app/239030/discussions/0/846963165520653258/)) | Day restarts (inferred) | Pick Day 1 or trash saves |
| Not Tonight | Per day; reload copies into a new slot, 3 slots ([Steam](https://steamcommunity.com/app/733790/discussions/0/3194747223957163518)) | Day-based | Delete a slot |
| Headliner: NoviNews | At sleep; reload rerolls the day's articles ([Knoef](https://knoef.info/trophy-guides/ps4-guides/headliner-novinews-trophy-guide/)) | Day restarts | Replay cycle |
| Orwell | Every action, survives Alt+F4 ([Steam](https://steamcommunity.com/app/491950/discussions/0/305509857568739839/)) | Resume exactly | New profile only |
| Reigns: Game of Thrones | Only at death ([GamingOnLinux](https://www.gamingonlinux.com/forum/topic/3860/)) | Back to last death | — |
| Blue Prince | End of day ([Steam](https://steamcommunity.com/app/1569580/discussions/0/599651004551572825/)) | Day lost | — |
| 2048 | Every move; cleared on game over ([game_manager.js](https://github.com/gabrielecirulli/2048/blob/master/js/game_manager.js)) | Resume exactly | "New Game", no confirm |
| A Dark Room | Every state change ([state_manager.js](https://github.com/doublespeakgames/adarkroom/blob/master/script/state_manager.js)) | Resume exactly | — |

The complaints mirror each other. Coarse checkpoints draw complaints about lost time. A Reigns player expected five-minute sessions and lost 20-minute reigns to interruptions ([GamingOnLinux](https://www.gamingonlinux.com/forum/topic/3860/)), and Blue Prince players leave their PCs running overnight rather than lose a day ([Steam](https://steamcommunity.com/app/1569580/discussions/0/599651004551572825/)). Per-action saves draw the opposite complaint: Orwell players wanted undo, or "at least... a confirm option" ([Steam](https://steamcommunity.com/app/491950/discussions/0/152392786900354473/)). Not Tonight shows that multi-slot schemes cost players too. Copy-on-reload filled all three slots, and one player "accidentally deleted my whole game" ([Steam](https://steamcommunity.com/app/733790/discussions/0/3194747223957163518)). David Sirlin's principle covers all three: players "should be able to stop playing your game anytime without losing their meaningful progress" ([Game Developer](https://www.gamedeveloper.com/design/saving-the-day-save-systems-in-games)).

A day-start checkpoint is defensible for a ~6-minute shift, but determinism tips the balance toward exact resume. Slay the Spire shows what a deterministic reload does. A mid-fight quit restarts the fight and "the cards come out in the exact same order" ([Steam](https://steamcommunity.com/app/646570/discussions/0/5208960061387585960/)). A refresh becomes a rehearsal with perfect foreknowledge. Here, the player would know which applicant carries the planted violation before the window opens. Blue Prince players independently proposed the fix: "As long as there is only one save and it loads at the exact same state there would be no way of exploiting it" ([Steam](https://steamcommunity.com/app/1569580/discussions/0/599651004551572825/)). So the recommendation keeps both precedents. Refresh resumes exactly, the web norm. Replaying today stays available, the Papers, Please norm, but only as a visible action that costs a full shift. No desk game found restores a running shift timer exactly. All of them restart the level (Papers, Please, Slay the Spire, Reigns) or charge for leaving it, like Candy Crush's lost life. So restoring the clock is a deliberate departure. It is justified because, once a decision log exists, the only extra cost is persisting one number.

## One localStorage key holds a seed and a list of stamps

**`localStorage` is the right store.** It allows **5 MiB per origin** and throws `QuotaExceededError` above that ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)), so a few-KB save uses about a thousandth of it. A 2015 benchmark measured 5.9 ms to write 500 KB ([Peterbe](https://www.peterbe.com/plog/localstorage-is-fast)), so a write at this size takes well under a millisecond. Being synchronous also helps: a write inside a `pagehide` handler finishes before the handler returns. `sessionStorage` dies with the tab. IndexedDB is async, and open connections block the back/forward cache ([web.dev](https://web.dev/articles/bfcache)). Neither earns its complexity. Browser storage fails in two ways. Safari deletes "all script-writeable storage after 7 days of no user interaction with the website," with home-screen web apps exempt ([WebKit](https://webkit.org/tracking-prevention/)), a policy in place since Safari 13.1 in March 2020 ([WebKit blog](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). Private windows clear storage when the last private tab closes, and blocked storage throws `SecurityError` even on the property read ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)). Chrome's team found that automatic clearing is rare and that users clearing storage by hand is far more common ([web.dev](https://web.dev/articles/persistent-storage)). Skip `navigator.storage.persist()`. Firefox shows a permission prompt, the guidance says never to request it on page load ([web.dev](https://web.dev/articles/persistent-storage)), and nothing found confirms that it overrides Safari's 7-day purge. Guard every read and write in try/catch, as MDN's `storageAvailable` pattern does ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API/Using_the_Web_Storage_API)) and as `src/ui/sound.ts` already does for `poh-muted`. When storage is unavailable, play on in memory. Use a new key, `poh-save`, so "Start the week over" never resets the mute flags.

**Save the log, not a snapshot. The code gives one decisive reason.** The reducer in `src/ui/week.ts` stores `decided[i]` against the i-th applicant of the day's queue, but the queue is not in `GameState`. `src/ui/Game.tsx` regenerates it from `generateWeek(seed)` on every load. A snapshot therefore does not survive a generator change either: old decisions would sit against new applicants. That removes the snapshot's usual advantage, and the log has three of its own. The pure reducer stays the only source of truth. The save is tiny. And a bug report can be the save JSON, replayed by the harness `src/replay.test.ts` already uses to play whole weeks. This is the classic command-replay pattern ([Game Programming Patterns](https://gameprogrammingpatterns.com/command.html)). Its known weakness is version binding. Factorio states that "Replays for worlds created in older versions cannot be played" ([Factorio Wiki](https://wiki.factorio.com/Replay_system)). Brogue CE declares saves incompatible across minor versions, and once shipped a special path that kept old behaviour for old saves ([BrogueCE changelog](https://github.com/tmewett/BrogueCE/blob/master/CHANGELOG.md)). The project's own notes say generator changes routinely shift seeded outcomes. So the failure to design against is a stale log landing the same stamps on different applicants, not a crash.

Don't log the reducer's `Action` objects as they are. `decide` carries a full `GeneratedApplicant`, and `close` and `next-day` carry the whole queue. Logging them would copy generated content into storage and replay stale applicants against a new rulebook. Log only what the player chose, and re-derive the applicant from the seed:

```ts
type Step = ['open'] | ['call'] | ['decide', Decision, RuleId?] | ['time-up'] | ['close'] | ['statement'] | ['next-day'];
type Save = {
  v: 1;              // shape of this JSON
  build: number;     // bumped by hand when gen/rules/content change outcomes; never a git SHA
  seed: number; startDay: number;
  log: Step[];       // every reducer input, including time-up from the clock
  clock: number;     // seconds of today's shift used (UI only, never a reducer input)
  check: string;     // fingerprint after replay, e.g. `${day}:${phase}:${called}:${savings}`
  savedAt: number;   // debug only
};
```

Loading follows six steps. Parse in try/catch. Check the shape with a hand-written guard, so no validation dependency is needed. Compare `build`. Replay the log from `startWeek(seed, startDay)` inside try/catch. Compare the fingerprint. If any step fails, move the blob to `poh-save-discarded`, start fresh, and show one deadpan line (kept in `src/content/`) saying the Ministry has revised its forms. Don't write migrations. A week lasts under an hour, and versioned generators are the kind of speculative abstraction AGENTS.md forbids. A git-SHA build id would discard saves after every CSS tweak. The fingerprint already catches the generator change nobody remembered to flag.

One failure mode is specific to this codebase. `App.tsx` wraps the game in an `OutOfOrder` error boundary. A save that passes validation but still crashes rendering would re-crash on every reload, and the player could escape only by clearing site data. The boundary's screen needs a "Start the week over" that clears `poh-save`.

## Write on every stamp, and again the moment the tab hides

**Write synchronously after every reducer change** from an effect keyed on state. Decisions arrive a few times a minute, so debouncing buys nothing and opens a window where a refresh loses the last stamp. React's StrictMode runs effects setup, cleanup, setup in development ([React](https://react.dev/reference/react/StrictMode)), and writing the same JSON twice is harmless. The clock ticks every 250 ms and must not go through that path. Checkpoint it on `visibilitychange` to hidden, on `pagehide`, and every ~5 s while running. Chrome's lifecycle guidance calls the hidden transition "often the last state change that's reliably observable," especially on mobile, where `beforeunload`, `pagehide` and `unload` are not fired when users close tabs or the browser app ([Chrome for Developers](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)). Don't touch `unload`. Chrome's deprecation reached **100% of page loads in Chrome 154 on 22 September 2026** ([Chrome for Developers](https://developer.chrome.com/docs/web-platform/deprecating-unload)). Don't add a `beforeunload` "are you sure?" prompt either: the same guidance limits it to pages with unsaved work, and an autosaving game has none.

**Two tabs will overwrite each other's week unless one of them yields.** The `storage` event fires in every same-origin document except the one that wrote ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API/Using_the_Web_Storage_API)). So any `storage` event on `poh-save` means another desk moved the week on. The tab that receives it should stop writing and show a notice ("This file is being processed at another desk") with a "Take this file back" button that reloads from storage. That is about twenty lines with no new API, and it works because the save fully describes the week. Web Locks with `ifAvailable` can detect a second tab at startup, before either writes ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)). It is optional. Never try to merge two logs, because they are two different weeks. Last-writer-wins with no UI is a defensible minimum for a local comedy game. The notice costs little and makes the clerk fiction work for it.

**Persist seconds used, not a deadline.** A wall-clock deadline (`endsAt = Date.now() + remaining`) keeps the shift running while the tab is closed. The player would reopen it tomorrow to a finished shift. That suits idle games, but here closing the tab is going on break. Seconds used also match the existing design: `useShiftClock` in `src/ui/Shift.tsx` already stops counting while `document.hidden`. The hook keeps `elapsed` in local `useState`, so it needs two changes: take the saved value as its starting point, and report it to the save code. `time-up` stays a logged reducer step. Persist only accumulated seconds, never a `performance.now()` value, because its origin resets on each page load.

The same hook likely has a latent bug, inferred and not reproduced. It advances `last` on every tick but adds the delta only when visible. Chrome throttles hidden timers to once a second, and to **once a minute after five minutes hidden** ([Chrome blog](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)). So the first visible tick after a long absence adds up to ~60 s of hidden time. A frozen page that thaws adds the whole frozen period. Clamping each tick's delta to about one second, or resetting `last` on `visibilitychange` and `pageshow`, fixes it.

## One shutter card serves pause, continue and start again

Players must never land on a destructive control by accident. In Papers, Please, Escape opens the pause menu ([GOG forum](https://www.gog.com/forum/papers_please/how_to_quit)). A search snippet, not a page that could be verified, reports that its pause menu stacks "Restart Yesterday" above "Restart This Day", and that players misclick. It is weak evidence, but it points at a real hazard. The design below keeps the safe action first and focused, and separates the two restarts in placement, wording and weight.

| Control | Where it lives | Guard | What it does |
|---|---|---|---|
| **Continue — Day 3 · Shift, 2:40 left** | Card on load, only when the log has progress | None; focused | Resumes; clock starts only on press |
| **Pause** | Escape, plus a visible corner button | None | Clock and music stop; shutter covers the desk |
| **Redo today's shift** | Pause card only | Undo notice until the first new stamp | Cuts the log back to this morning's Gazette |
| **Start the week over** | Quiet link on the card; separated in pause; primary button on the ending screen | Confirmation, except on the ending screen | Clears the save; Day 1 |

The loading card and the pause card should be one component: the morning shutter, down, with the saved point written on it. With no save, or an empty log, go straight to Day 1. The Game Accessibility Guidelines ask that a game start without "multiple levels of menus" ([GAG](https://gameaccessibilityguidelines.com/allow-the-game-to-be-started-without-the-need-to-navigate-through-multiple-levels-of-menus/)). With a save, the card is the visible confirmation players rely on: Laura Dale recommends "frequent autosaves with visible confirmation" ([Access-Ability](https://access-ability.uk/2022/04/25/checkpoints-save-states-and-save-availability/)). Space and Enter activate Continue, matching the existing advance keys in `src/ui/Screens.tsx`. Closing the shutter while paused matters for a timed inspection game. Timed puzzle games hide the board when paused so that pausing can't buy free study time ([HonestSudoku](https://github.com/honestarcade/HonestSudoku/issues/2)), and the core challenge here is reading evidence under time pressure. Pause is also the accessibility valve for the timer. Xbox's guidelines exempt core gameplay timers ([XAG 116](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/116)), but GAG asks that precise timing not be essential ([GAG](https://gameaccessibilityguidelines.com/do-not-make-precise-timing-essential-to-gameplay-offer-alternatives-actions-that-can-be-carried-out-while-paused-or-a-skip-mechanism/)). The clock already stops while the tab is hidden. Showing the pause card on return, instead of silently resuming, is a common convention, though no primary source requires it.

**Confirm only what destroys real progress, and make undo do the rest.** Microsoft's guidance treats a warning as justified for losing "a significant amount" of the user's time, "such as 30 seconds or more". It sets the safe choice as the default, bans OK/Cancel for confirmations, and allows "Don't show this message again" only for routine prompts ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/uxguide/mess-confirm)). NN/g warns that confirming routine actions trains people to click through, and asks for buttons that "summarize what will happen" ([NN/g](https://www.nngroup.com/articles/confirmation-dialog/)). Apple wants one- or two-word result verbs and reserves red destructive styling for actions people didn't deliberately choose ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/alerts)). The WAI-ARIA pattern puts focus on the least destructive action ([W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)). That has a concrete payoff here: a clerk who presses Space out of habit lands on "Keep my week", not on "Start over". So the week reset gets a real dialog. Its plain title is "Start the week over?". One line says what goes ("Days 1–3, 212 PNK and your registry will be shredded permanently"), and the buttons are "Keep my week" (focused) and "Start over". "Redo today" costs one shift, which clears Microsoft's 30-second bar. But the log makes it truly undoable: keep the cut tail until the first new stamp, and show "Undo" beside the new morning. NN/g and Microsoft both prefer undo to a dialog. The ending screen needs no confirmation at all, because nothing is lost there. Let the save sit on the ending, as Reigns: Game of Thrones does ([Steam](https://steamcommunity.com/app/897820/discussions/0/1733216261962922425/)), until the player chooses a new week.

**Escape closes things. It should never open Inspect.** Escape is the platform's close request, and it is what `<dialog>` and `CloseWatcher` respond to ([Chrome for Developers](https://developer.chrome.com/blog/new-in-chrome-120)). The conventional order is: close the confirmation, then close the pause card (resume), then leave Inspect, and only with nothing open, open the pause card. Today `src/ui/Shift.tsx:119` binds Escape to `toggleInspect()`, so pressing Escape on a normal desk *enters* Inspect. Escape should only exit Inspect, with `i` staying the toggle. That changes the controls, so it needs the owner's approval. The native `<dialog>` with `showModal()` gives Escape-to-close, an inert background and top-layer stacking with no dependency. The Shift's window-level keydown handler must still ignore A, C, Space, I and 1–6 while paused. Otherwise pressing A inside the dialog stamps the applicant behind it.

**Keep the jokes in the frame, not on the buttons.** A "Form 7-B: Request to Restart the Week" slip with a stamp fits the game's voice. Its title and buttons must still say the plain thing, because in-world synonyms like "File" or "Withdraw" recreate the "OK means what?" ambiguity the platform guides warn against. Two smaller decisions follow from the table. A Papers, Please-style branch tree isn't worth its interface debt. A linear "Replay from Day N" after the ending is cheap with a log, but optional. And today `?seed` defaults to 1 in `App.tsx`, so every player gets the same week. "Start over" with the same seed replays a known queue, which Papers, Please accepts for its scripted days. A fresh seed means a new week, and choosing between them is a gameplay decision.

## Test the refresh path before trusting it

Vitest runs in Node here, with no jsdom. That is an advantage: keep `loadSave`, `writeSave` and `restore` pure. Pass them a `Map`-backed fake `Storage` with a "throws `SecurityError`" switch, and test six paths: a round-trip, corrupt JSON, a wrong `v` or `build`, a fingerprint mismatch after a generator change, storage that throws, and "Redo today" truncating at the last `next-day`. Leaving jsdom out also avoids a known trap. Node 25's built-in `localStorage` shadows jsdom's in Vitest ([vitest #8757](https://github.com/vitest-dev/vitest/issues/8757)). That is irrelevant on the local Node 20.18.3, but it would appear with an upgrade. Load the save once, before `createRoot().render()`, and pass it in. Then there is no fresh-week flash, and StrictMode's double-invoked `useReducer` initializer ([React](https://react.dev/reference/react/useReducer)) neither replays the log twice nor fires the discard notice twice.

Playwright gives each test an empty browser context ([Playwright](https://playwright.dev/docs/auth)), so the core tests are simple. Stamp twice, call `page.reload()`, and compare `window.__game`. Close the page and open a new one in the same context. Install `page.clock` before `goto`, fast-forward three minutes, reload, and assert that roughly three minutes are used, not zero and not the full shift ([Playwright Clock](https://playwright.dev/docs/clock)). Whether `page.clock` survives a reload is undocumented, so spike that first. Don't seed a save with an unguarded `addInitScript`. It re-runs on every navigation, including `reload()` ([Playwright](https://playwright.dev/docs/api/class-page#page-add-init-script)), and would overwrite the very save under test. Instead, `evaluate` a `setItem` and then reload.

One existing test collides with this design and needs the owner's decision before implementation, and a second one constrains it. `e2e/slice1.spec.ts:67` reloads mid-shift and then clicks "Open the window". It encodes "refresh restarts the day", which exact resume deliberately breaks, and AGENTS.md forbids editing tests without asking. `e2e/slice2.spec.ts:32` reloads a morning with no actions taken. It keeps passing only if an empty log resumes silently, without the Continue card. The URL parameters need a rule too: resume only when the save's `seed` and `startDay` match `?seed` and `?day`, otherwise start that week fresh. Add a `?new` parameter that clears the save and strips itself with `history.replaceState`. In development, every worktree on `localhost:5175` shares one origin and one save. The build and fingerprint check will reject saves from other branches, which is the correct behaviour. But a stale dev server answering on the shared port will make a correct test look broken.

## Conclusion

The decision log turns every variant of "start again" into one operation: cutting a list. Redo today cuts at the last `next-day`. Start over empties the list. Replay from Day N cuts at day N. Undo keeps the cut tail. A bug report is the list itself. That is why the recommended system can offer Papers, Please's most loved feature, replaying days, without its branch tree, slot cap or corruptible header file. The research also moved the risk. The threat is not the browser losing a 3 KB save, since Safari's 7-day purge and private windows are the only common causes. It is the game silently reinterpreting a save after a generator change. Because the queue is regenerated from the seed rather than stored, a snapshot would not avoid that either, so the fingerprint check matters more than the choice of storage API.

Three points remain unverified. Papers, Please's exact pause-menu labels rest on a search snippet. The iPad port's mid-day resume doesn't say whether it restores the clock. And the hidden-tab clock jump is inferred from Chrome's throttling rules, not reproduced. Before building, the owner needs to approve four changes: Escape no longer entering Inspect, "Redo today" as a new gameplay feature, exact resume superseding the slice 1 reload assertion, and same-seed or new-seed for a fresh week.
